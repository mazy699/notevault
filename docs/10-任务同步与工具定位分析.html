任务同步与工具定位分析

关联：NoteVault Issue #25（任务管理同步 Jira） ·  日期：2026-11-27  ·  性质：分析稿 / 决策文档，未开发  ·  作者：Mazy + AI 协作整理

一页结论（TL;DR）

  • 三层定位：Jira 公司任务的唯一事实源（只读对待）；Linear 个人跨端收集站（手机/电脑同步：Jira 镜像 + GitHub issue + 想法速记）；NoteVault 本地深用层（周/月视图、worklog、复盘统计，永不同步出去）。
  • 推荐链路：Jira / GitHub ──Agent 定时搬运──▶ Linear（收集站）──NoteVault 拉取或 Agent 推送──▶ 周月视图。Jira → NoteVault 直连作为并行路线先做（即 Issue #25 原 Phase 1）。
  • Issue #25 结论：原方案成立，且数据模型已预留 external_source / external_id，天然支持把 linear、github 作为后续新源接入；建议补充「多源枚举 + 字段最小化镜像」两条调整，其余照做。
  • 关键路径判断：Jira→Linear 的同步不需要开发 NoteVault，用 Agent（如 ZCode 定时任务）+ 同步脚本即可实现（走 Jira MCP 读、Linear API 写）；Unito/Zapier 类第三方同步平台需要 Jira 管理员权限，公司账号基本不可行。
  • 先拍板再开发：第 7 节给出 6 个决策项，其中「公司数据镜像到个人 Linear 的合规确认」是硬前提。

3四个关键问题逐条解答

Q1 · Linear 和公司 Jira 怎么同步？（Jira 已配 MCP；公司账号权限小、无管理员）

三条候选路线，可行性差别很大：

路线机制可行性说明
① 第三方同步平台
Unito / Zapier / Exalate 等		 平台在 Jira 侧安装应用、建立双向同步规则 不可行 都需要 Jira 管理员安装应用或全局权限；公司账号只有基础任务权限，且公司数据经第三方平台中转风险更大
② Atlassian 官方 MCP 直连 mcp.atlassian.com（官方远程 MCP） 看 Jira 类型 官方远程 MCP 仅支持 Jira/Confluence Cloud；若是自建 Server/DC 则不可用，需改走社区 MCP（如 sooperset/mcp-atlassian，支持 PAT，用户级凭据即可）或直接 REST
③ Agent 定时镜像（推荐） Agent 定时跑同步脚本：Jira 侧读（MCP 或 REST + PAT），Linear 侧写（GraphQL API / 官方 MCP） 可行 只需要用户级凭据（自己的账号能看什么就同步什么），完全不需要管理员；增量按 updated 游标；脚本跑在自己机器上，数据不经第三方

推荐：路线 ③。落地形态很轻：

  • 一个同步脚本（Node/Python，放本机，比如仓库 scripts/ 或独立目录）；
  • 定时触发用现成能力（如 ZCode 的定时任务 / Windows 计划任务），工作时段每 15–30 分钟一次即可；
  • 幂等约定：Linear issue 描述头部嵌入 Jira key（如 [JIRA:PROJ-123]）或用固定 label jira-sync，同步前先按 key 查重，存在则更新、不存在则创建；
  • 方向约定：Jira → Linear 单向。在 Linear 里只查看、加个人备注，不改状态——状态以 Jira 为准，下次同步会覆盖回来。这样也回避了"个人账号写公司系统"的权限与合规问题；
  • 字段最小化：只镜像 标题 / issue key 链接 / 状态 / 优先级 / 截止日 / 父 Story 标题，不镜像描述全文与附件（既省空间也降合规风险）。

注：你已在 Linear 关联 GitHub——官方 GitHub 集成主要做 PR↔issue 关联与自动关闭，issue 的持续同步仍建议纳入路线 ③ 的同一个同步脚本（gh CLI 拉 issue → Linear API 建/更新），Jira 与 GitHub 用同一套游标与查重逻辑。

Q2 · Linear 能用 Agent 创建/更新任务吗？

能，而且有三条通道，按需选择：

通道认证能做什么适用场景
① 官方托管 MCP
https://mcp.linear.app/mcp		 OAuth 2.1 授权，或直接 Authorization: Bearer <API Key> 查找 / 创建 / 更新 issue、project、document、comment（另有 /mcp/readonly 只读端点） ZCode 等 MCP 客户端直接挂上即用，最省事
② GraphQL API + Personal API Key Linear 设置 → 安全与访问 → Personal API keys issueCreate / issueUpdate 等全部 mutation 同步脚本用这个：一个 HTTP 请求就能建/改 issue，最稳定可控
③ Agents API（"真 Agent 身份"） 需要注册 OAuth Agent 应用 以 Agent 身份发会话与活动（@-mention 交互等） 不需要。个人 API Key 不能发 agent activity，但我们的场景只需"创建/更新 issue"，通道 ①② 足够

结论：同步脚本走 ②（GraphQL + Personal API Key），日常让 ZCode 直接操作 Linear 走 ①（官方 MCP）。两者用同一个 API Key 也可以。

Q3 · 能统计任务吗？
  • Linear 原生统计：Insights 图表基本在付费档；免费档能力有限，且个人自用场景下原生图表并不针对"周/月复盘"设计。
  • Linear API 统计：可以全量拉 issue（含 createdAt / completedAt / assignee / cycle），想算什么都能算——但这正是别在 Linear 里重复造的理由。
  • NoteVault 才是统计主场：本地数据齐全（task + work_entry），周视图看"本周该做什么/做了什么"，月视图日历看节奏，配合 worklog 工时出个人报告。后续可在月视图加简单统计（本周完成数、工时合计、按项目分布），成本很低且完全私有。

建议分工：Linear 只做"今天/最近"的查看与勾选；所有统计与回顾都收敛到 NoteVault。

Q4 · NoteVault 任务工作台能支持 AI Agent 直接创建/更新任务吗？

现状不能——NoteVault 目前对外没有任何 Agent 可调用的接口。但有三个可选方案，都不复杂：

方案 A · 本地 Agent HTTP API（推荐首选）

Web 版宿主本来就跑在 127.0.0.1:8321（node:http），增加一个本地 token 保护的 Agent 端点（如 POST /agent/task），内部复用现有 call(cmd, payload) 命令契约；桌面版按双宿主惯例同步登记（shared/types.ts / client.ts / web/server.ts / api.rs 四处）。

Agent 用 curl 就能建/改任务；桌面端开着时同样可达（同端口约定）。

优点：改动小、契约清晰、和现有架构零冲突。约束：只绑 127.0.0.1、必须带本地 token、只开放白名单命令。

方案 B · NoteVault 本地 MCP Server

写一个 stdio MCP server 小进程，把"建任务/改状态/查周视图数据"暴露为 MCP tools，任何支持 MCP 的 Agent（ZCode、Claude 等）都能直接调用。

优点：最通用，Agent 体验最自然。代价：多一个常驻进程和一套配置，工作量比 A 大。

方案 C · NoteVault 拉 Linear（拉模式）

给 NoteVault 加"Linear 同步"设置（与 Issue #25 的 Jira 同步同构：PAT + 增量游标 + upsert），NoteVault 主动定时拉 Linear。

优点：不依赖 Agent 在线，纯 NoteVault 内部闭环。缺点：Agent 不能"即时"写入，实时性差一档。

推荐组合

C 先行、A 跟进：C 与 Issue #25 的 Jira 拉取是同一套代码骨架（只换源），边际成本最低；A 作为第二阶段补上"Agent 即时写入"能力。B 可以后置，等真有跨工具 MCP 编排需求再说。

安全底线（无论 A/B）：token 仅存本地设置、UI 打码、日志脱敏；接口只接受白名单命令；任何写操作不影响"本地条目不被覆盖"原则。

4Issue #25 方案重审（引入 Linear 后的调整）

4.1 仍然成立的部分

  • Phase 1 = Jira → NoteVault 直连只读：路线不受 Linear 影响，依然是第一优先——它最快让周/月视图有公司任务，且不依赖个人 Linear 可用性。
  • 数据模型已预留多源：原方案给 task 增加 external_source / external_id / external_url / external_parent_key… 并建唯一索引——这正是"Linear / GitHub 作为新源"所需要的全部字段，不需要返工。
  • 同步策略（增量游标、幂等 upsert、失败保留旧数据、无后台常驻）、安全约束（token 本地、宿主代理限域）原样保留。

4.2 建议的调整

调整点建议
external_source 取值 直接定义为枚举 "jira" | "linear" | "github" | "manual"（迁移注释里写明，虽然 Phase 1 只会写入 jira）。周视图/详情的来源徽标按源显示不同图标与链接格式。
收录规则（原待确认问题 3） 多源下规则统一：周视图 = 有时间窗（Jira duedate / Linear due date）或本周已有条目的任务都收录；月视图 = 计划 chip（按 due date）+ 每日侧栏"外部待办"列表。两个视图都能看到"纯导入、还没记 worklog"的任务——这是 Issue #25 已识别的关键点，多源后更重要。
Agent 写入通道 方案 A（本地 Agent HTTP API）拆成独立小 issue，不塞进 #25 的 Phase 1，避免范围膨胀。
Linear 源的字段映射（预留） Linear issue identifier（如 ME-12）→ external_id；url → external_url；state → status；project → project；父 issue → external_parent_key/summary；due date → 时间窗。与 Jira 映射表并列，实现时只是多一张映射配置。
合规与字段最小化 无论直连还是经 Linear，NoteVault 侧同样遵循"只镜像元数据字段"原则；描述按需懒加载（点开详情再拉），不落地全文。
