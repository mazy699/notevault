Git 分支与开发流程：单人 + AI 协作版

项目：NoteVault（本地 AI 文档查看器 · Web + 桌面双宿主） ·  日期：2026-11-28 ·  性质：流程决策稿，不改代码 ·  关联：AGENTS.md §1 开发流程

一页结论（TL;DR）

  • 不要加常驻 dev 分支。单人项目里它买不到新能力，只会多一次合并、多一条会漂移的线。你缺的不是分支层数，是自动化和清理。
  • 主干模型保持不变：main 永远可发布 + 短命 feature/* + PR 合并 + 打 tag 发布。这已经是业界说的 Trunk-based / GitHub Flow。
  • 从公司流程里只借两样：① 固定的发布窗口（周节奏，攒批发布）；② 需要冻结时才切的短命 release/x.y.z（桌面打包、杀软误报验证、大版本上线）。
  • 用 tag 代替 dev 表达“已集成但没发布”的状态：tag 是不可变快照，零合并成本；dev 是可变的线，要一直养着。用门禁 + CI 代替 test 分支：你的测试环境就是本机。
  • 核心差别不在分支数量，而在分支寿命：公司的分支以“项目 / 周”为单位，所以要靠“回流下发”续命；你的分支以“小时 / 天”为单位，合并即删，回流成本自然趋近于零。

01先想清楚：分支到底在解决什么问题

分支不是“规范”，它是一种隔离手段。每开一条长命分支，你就欠下一条“同步边”：这条线越久不合，合并冲突越多，越需要人工“回流”。所以判断标准很简单——这条隔离边界，你是否真的需要？

要隔离的东西 公司靠什么解决 你靠什么解决
半成品代码
不能进主干		 feature 分支（多人各占一条） 一样 feature 分支，但只活 1~3 天
集成缓冲
合了但还不能发		 dev 分支 / 项目 release 分支 tag + main 合并进 main 即“已集成”，tag 标记“已发布”，中间态不需要分支
发布冻结
只修 bug，不进新功能		 release 分支 + 测试分支 按需 切 release/x.y.z，2 周内必须收口
环境对应
测试环境 / 生产环境		 test 分支部署测试环境，main 部署生产 门禁 + 预览构建 本机跑测试环境，打包产物即验收对象
多人并行
各写各的不打架		 feature + release + dev 多层 不存在 只有你一个（外加 AI 代理，但代理也用短命分支）

两个关键认知

① 分支是可变指针，tag 是不可变快照。想表达“这一版就是当时那样”，用 tag；想继续在上面改，才用分支。很多团队用 dev 分支做的事（标记一个可测试的版本），一个 tag 就能做，而且不用合并、不会漂移。

② 分支拓扑不产生质量。质量来自合并前的门禁（tsc --noEmit、vitest、34 项桌面冒烟、打包安装验证）。多加一层 dev，门禁该漏还是漏，只是漏得更晚、更难定位。

02现状盘点：你其实已经比“加 dev”更接近正确形态

先按仓库事实说话（2026-11-28 检查）：

项目 现状 评价

发布方式 chore/release-vX.Y.Z 分支改版本号与发布说明 → 合 main → 打 tag → gh release 事实上就是“短命发布分支”
门禁 npx tsc --noEmit、npx vitest run、cargo run -- --smoke（34 项）、双主题截图、安装包冒烟 门禁成色很足
main 保护 未开启（GitHub 返回 Branch not protected） 建议开启
CI 仓库无 .github/workflows，门禁全靠本地手动跑 最大风险点

结论：你现在这套不是“很基础”，而是“骨架对了、肌肉没长”。真正要补的是 CI 自动门禁、main 分支保护、分支清理 和 发布节奏，而不是再加一层 dev。加 dev 反而会把已经理顺的“主干始终可发布”破坏掉。

03拆解公司流程：每一环为什么存在，单人是否成立

公司的流程不是“更标准”，而是“为更大的协作规模付的税”。逐环看它解决的是谁的问题：

读法：项目开始时从 main 切一条 release 分支，各任务在 feature 分支上并行，合回 release；release 随时合入 test 供测试；整项目完成后 release 合 main 上线。多条 release 之间还要互相“回流下发”。

环节 在公司里解决什么 单人是否成立 你的替代方案
main 生产环境唯一事实源，任何 tag / 发布都从它出 完全成立 保留。并强化“随时可发布”这条性质
test 共享测试环境：测试同学 + 产品在固定地址验收，开发不占环境 不成立 没有第二个人验收，也没有共享环境。用本地门禁 + 打包产物验收替代；Web 版本机启动即可
release 项目级冻结：多个任务先攒在一条线上，整体测完再上线；多人共享同一集成点 仅冻结期成立 平时不需要；需要冻结时切短命 release/x.y.z（见第 06 节）
feature 隔离半成品，互不阻塞 完全成立 保留，但寿命压到 1~3 天
周发布窗口 批量上线：把非紧急的修复攒一周，降低发布次数和风险 可选成立 保留“窗口”这个概念，去掉每周一条分支：合进 main 攒着，到窗口日打 tag
hotfix 绕过测试队列，直接从 main 修复并上线 成立 保留，但路径与普通修复相同：fix/* → PR → main → patch tag；只是不等窗口
回流下发 多条长命 release 分支并行，必须定期互相同步，否则合并冲突爆炸 不成立 分支短命 + 每日 rebase origin/main，没有需要回流的线

一句话：公司流程的复杂度来自 多人 + 多环境 + 多项目并行。这三样你都没有，照搬只会得到它们的成本（双重合并、双线漂移、版本号打架），得不到它们的收益（并行、验收分工、发布统筹）。

04核心问题：到底要不要加 dev 分支？

4.1 结论

不加。除非满足 4.4 的触发条件（满足两条以上再重新评估）。单人 + AI 代理的仓库，dev 是一个“看起来更安全、实际只增加延迟和漂移”的中间层。

4.2 dev 想解决的问题，你已经有更便宜的答案

dev 分支常被赋予的职责你现有的替代成本对比
隔离“还没做完的活” feature 分支（本来就是干这个的） 相同
标记“已集成、待发布”的版本 main 上的一个 commit + tag；要构建就从 tag / commit 构建 更便宜
提供一个可测试的快照 tag 构建、或 PR 预览构建 更便宜
让“稳定版”和“开发版”并存 tag + 版本号（v1.4.0 / v1.5.0-beta.1） 更便宜

4.3 加 dev 的五笔真实成本

1
双重合并feature → dev 一次，dev → main 再一次。冲突要么解两遍，要么在第二次合并时集中爆发，而且爆发时你已经在“要发布”的节点上了。
2
双线漂移main 停在旧版本等发布，dev 一路向前。此时线上出 bug，修复要进 main、进 dev、还可能进 release——一份修改三个落点，这正是公司流程需要“回流下发”的原因。
3
发布基准含糊tag 打在 dev 还是 main？打在 dev 上，main 的历史就不代表“线上是什么”；打完再把 dev 合回 main，tag 指向的可能是 dev 的合并提交而不是 main 上的提交。查问题时永远要多问一句“这版到底从哪出的”。
4
门禁翻倍tsc、vitest、34 项桌面冒烟、打包安装验证都不便宜。合并点从 1 个变 2 个，每个都要跑一遍全量门禁；漏跑一次，问题就会晚一个环节才暴露。
5
main 失去“永远可发布”这是主干开发最值钱的性质：想发就发、随时能发、发了不用等。一旦 dev 成为默认落点，main 就变成“上次发布时的样子”，紧急修复立刻变复杂。省下来的时间，远大于多一层分支带来的心理安全感。

4.4 什么情况下才该加（触发条件）

不要凭感觉，用可观察的条件判断。满足两条以上，再考虑引入第二条长命线：

  • 第二个人加入，且需要共享一个“非生产”的集成点；
  • main 开始自动部署生产（这时才需要一条 staging 线挡在前面）；
  • 需要长期并行维护两个版本（如 v1 只修 bug、v2 大改，且 v1 还要持续发版）；
  • 外部冻结期：应用商店审核、客户验收窗口，期间主干不能动；
  • 有非开发者参与验收，且必须给对方一个稳定可访问的版本。

即使满足了，也优先用有明确退出条件的分支，而不是常驻 dev：release/1.5（上线后删除）、next（v2 合并后删除）、staging（仅当存在真实 staging 环境）。能删的分支才是好分支。

4.5 “中间加一层 dev 会更安全吧？”

直觉：多一层缓冲，出错概率更低？

恰恰相反。缓冲层不会拦截错误，只会推迟发现。错误从“合并进 main 时 5 分钟发现”变成“发布前一天发现”，修复成本更高，且那时你面对的是积压了一周的 diff。

真正降低出错概率的是三件事：合并前必须过门禁（CI）、main 不许强推/直推（分支保护）、每次合并的 diff 足够小（短命分支）。这三件都与 dev 无关。

05方案对比：三种候选，选哪个

维度 方案 A · 主干 + 短命特性分支
（现状）		 方案 B · main + dev + feature
（你想问的）		 方案 C · 主干 + 按需 release/x
（推荐升级）
长命分支数 1（main） 2（main、dev） 1~2（main，冻结期多一条 2 周的分支）
每个功能的合并次数 1 2 1（冻结期内的修复多一次）
发布基准 main 上的 tag，唯一且清晰 含糊：dev 还是 main？ main 上的 tag；release 分支只做冻结，最终仍回 main 打 tag
漂移 / 回流成本 低（分支平均活 1~3 天） 持续存在，且随项目变大 低，只在冻结窗口内存在

结论 现在就用 不推荐 需要冻结时切换

建议：默认跑方案 A；遇到“需要冻结验证”的版本（尤其是桌面安装包 + 杀软误报验证，见 docs/05-杀毒软件与发布说明.md）临时切到方案 C，冻结结束立刻回到 A。不要采用方案 B——它是给多人团队设计的，单人用只会拿到它的全部成本。

顺带说明：完整的 Git Flow（main / develop / release / hotfix / feature 五类分支）对你更不适用，它诞生于“有版本发布窗口、多人并行、需要长期维护多个已发布版本”的桌面软件时代。你的发布频率和协作规模都撑不起它的仪式感。

06NoteVault 的落地方案

6.1 分支类型与寿命（建议写进 AGENTS.md 的补充）

读法：日常只有 main 一条长命线；feature 从 main 拉出、合回 main 后删除。只有当版本需要冻结验证时，才从 main 切一条 release/x.y.z，期间只收修复，验证完成后合回 main、在 main 上打 tag、删除该分支。

分支 从哪来 合到哪 寿命上限 用途 / 规则
main — — 永久 始终可发布；只接受 PR；禁强推；每个 tag 都从这里出
feature/<主题> main main 3 天 新功能 / 多文件改动；超期就拆分或先合一部分
fix/<主题> main main 1 天 普通 bug；紧急时也走这条路，只是不等发布窗口
docs/<主题> main main 3 天 文档 / AGENTS.md / 分析稿；同样走 PR，不直推
chore/release-vX.Y.Z main main 1 天 版本号 + 发布说明 + 必要的构建配置；合并后立即打 tag
release/X.Y main main 2 周 仅冻结期使用：只收修复，不收新功能；验证完合回 main 并删除

6.2 主干规则（八条）

R1
main 永远可发布任何时刻从 main 打包都应该是能用的版本。做不到时，说明有东西该放 feature 分支而不是 main。
R2
一切都从 main 拉，合回 main没有例外，没有“先合 dev”。这条最简单，也最能防止流程腐化。
R3
分支短命：目标 1 天，上限 3 天超过 3 天说明任务太大，拆成可独立合并的小步。短命是“不需要回流机制”的唯一原因。
R4
合并前必须过门禁tsc --noEmit + vitest run；涉及 Rust/宿主加 cargo run -- --smoke；涉及 UI 加双主题截图目检。门禁不过不允许合并。
R5
一律 PR + --merge即使是自己合并也走 PR：留下 diff、留下讨论、留下“为什么改”的记录，也给 AI 代理划定不可直推的边界。
R6
tag 只打在 main 上，且永不移除发布 = main 的某个 commit + 语义化 tag vX.Y.Z + Release 说明。tag 是唯一“这版是什么”的答案。
R7
合并即删分支本地和远端都删。分支列表应该只有 main（以及冻结期的 release），一眼看得懂。
R8
长命分支必须有退出条件如果确实要开 release/next，写下“什么时候合回、什么时候删除”。没有退出条件的分支，就是下一个 dev。

6.3 日常循环

选任务 → 从 main 切分支 → 小步提交 → 每日 rebase main → 本地过门禁
   → 推送 → PR（自审 diff）→ 合并 --merge → 删分支 → 回 main 对齐

对应到一周的节奏（可按需调整，不是硬性规定）：

周一~周四  feature/fix 随时合入 main（不攒、不排队）
周五        chore/release-vX.Y.Z：改版本号 + 写发布说明 → 合 main → 打 tag → Release
任意时刻  紧急修复：fix/* 直接 PR → main → 立即打 patch tag（不等窗口）
需要冻结时 从 main 切 release/X.Y → 只收修复 → 验证 → 合回 main → tag → 删分支

关于“每周固定发布窗口”的借鉴：公司用一条每周的 release 分支来承载它，你不需要那条分支——main 就是那条分支。窗口只是一条时间规则：“周五之前合进 main 的，这周发；周五之后合的，下周发。” 发布动作本身仍然是 chore/release-vX PR + tag，和你现在的做法完全一致。

你现在其实已经在用公司的“周发布分支”了，只是它叫 chore/release-v0.9.0，而且活得很短——这正是它比公司版本更健康的地方。

6.4 两种发布模式

模式一：常规发布（默认）

  1. chore/release-vX.Y.Z 从 main 拉出
  2. 改版本号（package.json、src-tauri/Cargo.toml、tauri.conf.json）
  3. 写 docs/release-notes-vX.Y.Z.md
  4. PR → 合并 main
  5. 在 main 上打 tag，推送 tag
  6. 构建产物 + checksums，gh release create
  7. 删分支

全程没有 release 分支。多数版本走这条。

模式二：冻结发布（按需）

  1. 从 main 切 release/X.Y
  2. main 只收紧急修复，新功能暂停合入（或照常合入但明确不进本版）
  3. release 上只收修复，逐条验证（安装包、杀软、WebView2）
  4. 全部通过后，release 合回 main
  5. 在 main 上打 tag，构建发布
  6. 删除 release 分支

适用于桌面安装包验收、杀软误报排查、大版本（v1.0）上线。

冻结期的纪律：release 分支存在的每一天，都在制造漂移。所以给它设硬上限（2 周），并且只允许修复进入。一旦开始往里面塞新功能，它就会变成公司流程里那条需要“回流下发”的长命分支。

6.5 紧急修复路径

git switch -c fix/xxx main        # 永远从 main 拉
# 改代码 + 跑门禁
gh pr create --base main --head fix/xxx
gh pr merge <PR号> --merge
git switch main && git pull --ff-only
git tag -a vX.Y.(Z+1) -m "hotfix: ..." && git push origin vX.Y.(Z+1)
# 若是冻结期：同样的修复也要合入 release/X.Y（或反过来从 release 修完再回 main）

注意：你不需要一条独立的 hotfix 分支类型。紧急与否只影响“是否等发布窗口”，不影响分支路径。

6.6 与 AGENTS.md 的关系

AGENTS.md 里“禁止直推 main、必须特性分支 + PR”的规定，本质上是给 AI 代理设的护栏，而不是多人协作需求。它恰好也是单人开发最该保留的一条：代理跑偏时，PR 是你最后一道人工检查点。不要因为“反正只有我一个人”而放开直推 main。这也是不建议加 dev 的另一个理由——如果代理可以直推 dev，护栏就形同虚设；如果代理也只能走 PR，dev 又没有存在意义。

07操作手册（可直接复制）

7.1 开分支与同步

# 从最新 main 开分支
git switch main && git pull --ff-only
git switch -c feature/短主题

# 每天开工前：把自己的分支垫到最新 main 上（替代“回流下发”）
git fetch origin
git rebase origin/main

# rebase 后推送（仅自己的分支可强推）
git push --force-with-lease

7.2 合并前自检

npx tsc --noEmit
npx vitest run
# 涉及 Rust / 宿主：
cd src-tauri && cargo run -- --smoke
# 涉及 UI：Web 与桌面端目检 + 深浅主题截图

7.3 PR 与合并

git push -u origin feature/短主题
gh pr create --base main --head feature/短主题
gh pr merge <PR号> --merge

# 合并后对齐并清理
git switch main && git pull --ff-only
git branch -d feature/短主题
git push origin --delete feature/短主题

7.4 发布

git switch -c chore/release-v0.10.0 main
# 改版本号 + 写 docs/release-notes-v0.10.0.md
gh pr create --base main --head chore/release-v0.10.0
gh pr merge <PR号> --merge

git switch main && git pull --ff-only
git tag -a v0.10.0 -m "v0.10.0"
git push origin v0.10.0

# 构建 + 校验 + 发布（发布动作需用户确认）
npx tauri build
node scripts/pack-portable.mjs
gh release create v0.10.0 --notes-file docs/release-notes-v0.10.0.md <产物>

7.5 冻结期（需要时才用）

git switch -c release/0.10 main
# 只收修复，逐条验证安装包 / 杀软 / WebView2
gh pr create --base main --head release/0.10   # 验证完成后合回 main
gh pr merge <PR号> --merge
git switch main && git pull --ff-only
git tag -a v0.10.0 -m "v0.10.0" && git push origin v0.10.0
git branch -d release/0.10 && git push origin --delete release/0.10

7.6 一次性清理与加固

# 看哪些本地分支已合入 main（可安全删除）
git branch --merged main

# 批量删除已合并的本地分支（排除 main）
git branch --merged main | grep -v '^\*' | grep -v ' main$' | xargs -r git branch -d

# 清理远端已不存在的追踪分支
git fetch --prune

GitHub 侧建议开启 main 分支保护（Settings → Branches → Add branch protection rule）：

  • Require a pull request before merging（批准人数可设为 0，单人也能自己合，但强制走 PR）；
  • Do not allow force pushes；
  • Do not allow deletions；
  • （可选）Require status checks to pass，等 CI 就绪后勾选。

08用门禁 + CI 替代 test 分支

公司需要 test 分支，是因为测试环境要部署、要有人点、要和开发环境隔离。你没有这些约束，但有另一个更真实的风险：忘记跑门禁。人（和代理）都会忘，唯一不会忘的是 CI。

你现有的门禁

  • npx tsc --noEmit 零错误
  • npx vitest run 全绿
  • cargo run -- --smoke 34 项（涉及宿主时）
  • cargo test --lib（涉及 Rust 时）
  • Web + 桌面双端实测，深浅主题截图目检
  • 安装包本机安装冒烟（发布前）

建议补充：最小 CI

不需要自动发布，只做“PR 上必须绿”。仓库目前没有 .github/workflows，这是当前流程最大的缺口。

name: ci
on:
  pull_request:
  push:
    branches: [main]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npx tsc --noEmit
      - run: npx vitest run

Tauri 冒烟依赖 Windows + WebView2，放在本地或 self-hosted runner；Linux runner 上意义不大。

Web 版的“测试环境”怎么办？本机 重新构建并启动NoteVault-Web版.bat 就是你的测试环境。需要给别人看时，用一次性的预览部署（或临时隧道），而不是维护一条 test 分支——那条分支一旦存在，你就会开始需要“把 test 合回 main”的仪式。

09常见坑与对策

坑 症状 对策
长命 feature 分支 合并时几十个冲突，改到怀疑人生 3 天上限 + 每日 rebase；超期就拆成可独立合并的小步
分支不删 19 条本地分支，不知道哪条还有用 合并即删；每周 git fetch --prune + --merged 清理
tag 打错位置 Release 资产和 tag 对应的代码对不上 tag 只打在 main 上；打之前 git pull --ff-only 并确认 HEAD
版本号撞车 两个 release PR 都改成 0.10.0 先合的先占号；后合的 rebase 后改成下一个号
merge / squash 混用 历史难追溯，rebase 时反复冲突 统一 --merge（AGENTS.md 已定），不要中途换
发布产物未验证 用户装完打不开 / 被杀软删掉 打包后本机安装冒烟 + 校验 checksums，再发 Release
把 main 当草稿 某次想发版，发现 main 编译不过 门禁 + 分支保护；main 上任何 commit 都必须能构建
