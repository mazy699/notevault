# NoteVault · 性能与资源占用

> 数据为 2026-11-20 在本机（Windows 10.0.26300 x64, Node 22.23.1, rustc 1.98.1）实测，
> 使用 Windows `Win32_Process.WorkingSetSize`（工作集）统计。

## 结论速览

| 指标 | 优化前 | 优化后 | 改善 |
| --- | --- | --- | --- |
| 首屏加载 JS | 2382 KB | **826 KB** | **-65%** |
| 首字节内容渲染 (FCP) | 224 ms | **164 ms** | -27% |
| 桌面空状态内存 | 503 MB | **416 MB** | **-17%** |
| Web 宿主进程内存 | 38 MB | 38 MB | —（已很轻） |
| 桌面 exe 体积 | 9.2 MB | 9.2 MB | — |

## 一、启动与加载优化

### 1. 拆掉渲染栈的启动期加载（最大收益）

**问题**：`Sidebar.tsx` 为了用一个 `findInTree` 工具函数，静态 import 了 `MarkdownView`，
导致 react-markdown / rehype 全家桶 / KaTeX / highlight.js 在**应用启动时就全部加载**。

**解决**：
- 抽出 `src/lib/links.ts`（纯路径/链接工具，无渲染依赖），Sidebar 改从那里导入；
- `MarkdownView` 改为 `React.lazy` 按需加载（打开第一个 Markdown 文件时才拉取）；
- `HtmlView` / `ImageView` 拆到 `SimpleViews.tsx`（轻量，随时可用）。

**效果**：首屏 JS 2382 KB → **826 KB**。

### 2. Mermaid / Cytoscape 二级懒加载

Mermaid 内核 ~92KB + Cytoscape 431KB（仅架构图/状态图使用）原先随 MarkdownView 一起加载。

**解决**：`MermaidBlock` 改为 `React.lazy`，只有在文档**确实包含 mermaid 代码块**时才加载。

**实测验证**：

| 场景 | JS 累计加载 | mermaid | cytoscape |
| --- | --- | --- | --- |
| 应用启动 | 826 KB | ✗ | ✗ |
| 打开普通 Markdown | 1603 KB | ✗ | ✗ |
| 打开含 Mermaid 的文档 | 3266 KB | ✓ | ✗ |

### 3. KaTeX 样式按需引入

`katex.min.css` 从全局 `index.css` 移到 `MarkdownView.tsx`，随渲染栈懒加载。

## 二、桌面版内存优化

### 现象与归因

桌面版（Tauri + WebView2）总内存 ≈ 416 MB，构成：

| 进程 | 内存 | 说明 |
| --- | --- | --- |
| msedgewebview2 (browser/main) | ~130 MB | WebView2 内核主进程，**固定开销** |
| msedgewebview2 (gpu) | ~88 MB | 原 182 MB，经参数调优后降至 88 MB |
| msedgewebview2 (renderer) | ~87 MB | 页面渲染（含已加载的 JS） |
| msedgewebview2 (utility ×2) | ~61 MB | 网络/存储等服务 |
| crashpad | ~13 MB | 崩溃收集 |
| notevault.exe | ~38 MB | Rust 主程序（含 WebView2Loader） |

**关键结论**：内存主体是 WebView2（Chromium 内核）的固定基线，
而不是我们的应用代码——即使空状态（未打开任何文件）也约占 500 MB。
这是 Tauri / Electron 类方案使用系统浏览器内核的固有成本，
用同样的 Chromium 内核，任何应用都无法低于此基线。

### 已实施的调优（`src-tauri/src/main.rs`）

启动前注入 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`：

| 参数 | 作用 |
| --- | --- |
| `--disable-gpu` + `--disable-gpu-compositing` | 纯文本阅读场景不需要 GPU 加速，主进程/GPU 进程内存显著下降 |
| `--disable-software-rasterizer` | 关闭软件光栅化的额外缓冲 |
| `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection,CalculateNativeWinOcclusion` | 关闭用不到的 UI/PDF/智能屏/遮挡计算功能 |
| `--disable-extensions` / `--disable-sync` | 无扩展、无账号同步需求 |
| `--disable-breakpad` | 关闭崩溃上报缓冲 |
| `--renderer-process-limit=1` | 限制渲染进程数为 1（单页应用足够） |
| `--js-flags=--max-old-space-size=192` | 限制 V8 老生代堆上限，防止异常文档撑爆内存 |
| `--disable-background-timer-throttling` / `--disable-renderer-backgrounding` | 保证后台时自动刷新轮询不被节流 |

**效果**：503 MB → **416 MB**（-17%），且经截图验证 Mermaid 图表、代码高亮、
表格渲染在软件渲染下**画质完全无损**。

> 说明：`--disable-gpu` 无法完全消除 Chromium 的 GPU 进程（内核仍会保留一个
> 用于合成的进程），但可将其内存从 182 MB 压到 88 MB。若后续发现某些机器上
> 渲染异常，可通过设置同名环境变量覆盖本应用的默认参数。

## 三、前端内存控制

### 内容缓存 LRU 上限

原先 `tabs.content` 缓存无上限，长会话里逐个打开大文件会导致内存持续增长。
现在缓存上限 **12 个文件**，超出时按插入顺序淘汰最旧条目，
但**当前已打开标签的内容始终保留**（避免切换标签时反复重读）。

### 已有的大小保护

| 保护 | 值 |
| --- | --- |
| 单文件读取上限 | 5 MB（超出只读前 5MB 并提示） |
| 搜索跳过文件 | > 2 MB |
| 自动刷新快照 | > 8000 文件时报告 truncated |
| 目录树节点 | 20000 上限 |
| 搜索文件数 | 3000 上限 / 命中 600 条上限 |

## 四、Web 模式资源占用

Web 版由 Node 进程提供服务，实测 **~38 MB**（WorkingSet），几乎可忽略。
浏览器标签页本身另计（与任何网页相同）。

若在意浏览器侧内存，可关闭「自动刷新」开关（省掉每 4 秒一次的全库快照扫描）。

## 五、进一步优化的空间（未实施，按需）

| 方向 | 预估收益 | 代价 |
| --- | --- | --- |
| 目录树虚拟化 | 超大库（>5000 文件）过滤更流畅 | 需引入窗口化渲染，约半天工作量 |
| 搜索移入 Worker（Web 宿主） | 搜索期间不阻塞 UI | 需拆分服务端逻辑，约 1 天 |
| 增量快照（只 stat 已打开文件目录） | 自动刷新 CPU 降低 | 需维护目录监听，复杂度上升 |
| 精简 highlight.js 语言集 | MarkdownView chunk 再省 ~100KB | 需精确映射 lowlight 语言注册 |
| 用 WRY 的 window 级参数替代环境变量 | 参数更可控 | Tauri 2 暂无该配置项 |

以上均为锦上添花；当前版本在「AI 文档查看」这一典型场景下已足够轻快。

## 六、v0.6.1 复测（2026-11-21，含密码工作台后）

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| 首屏 JS | **417.9 KB**（gzip ~136 KB） | index+react+runtime+jsx-runtime；密码/对比工作台均为懒加载 |
| 密码工作台 chunk | 33.3 KB | 仅在切到该工作台时加载 |
| 对比工作台 chunk | 30.3 KB | 仅在切到该工作台时加载 |
| Markdown 渲染栈 | 777.0 KB | 仅在打开第一篇 Markdown 时加载 |
| 桌面空闲内存（进程树） | **427.6 MB** | 宿主 38.2 MB + WebView2 子进程 ~389 MB |
| 桌面空闲 CPU | **0.63%**（单核） | 5 秒采样 31 ms |
| Web 宿主进程（node） | 49 MB WorkingSet / 52.9 MB 私有 | 累计 CPU 0.3 s（长时间服务后） |
| Web 宿主空闲 CPU | 0.00% | 无请求时零占用 |

结论：密码工作台对体积与内存的影响可忽略（+33 KB 懒加载 chunk，不进入首屏）；
桌面内存相较优化后基线（416 MB）增加 ~2.8%，属新功能代码与 WebView2 正常波动。

复测脚本：`scripts/measure-mem.ps1`（进程树内存）、`scripts/measure-cpu.ps1`（空闲 CPU）。
